# WorLibrary 跨端客户端开发方案

> 本文是 Web、桌面和移动端开发的共同约定。后续 Agent 在新增客户端能力前，应先阅读本文与 `docs/project-guide.md`。

## 1. 要解决的问题

WorLibrary 当前是一个 Web/PWA 阅读器：用户通过浏览器使用它，也可以将它安装为 PWA。产品下一步希望支持：

- 桌面端：Windows、macOS（后续可考虑 Linux）；
- 移动端：iPhone、iPad、Android；
- 同一用户在不同设备上继续阅读，并看到自己的进度、摘录和设置。

目标不是为每个平台重新开发一套阅读器，而是复用同一套 React 阅读界面和核心业务逻辑，再为各个平台补齐必要的系统能力。

```text
同一套 WorLibrary 阅读器
        ├─ Web / PWA：在浏览器运行
        ├─ Desktop：Tauri 包装为 Windows / macOS 应用
        └─ Mobile：Capacitor 包装为 iPhone / iPad / Android 应用
```

## 2. 核心决策

### 2.1 同一个仓库维护

桌面端和移动端应与现有 Web 应用放在同一 Git 仓库维护。三端共享阅读器、数据模型、认证、同步、翻译和 OCR 请求代码；同仓库可以避免各端修复不同步。

不应在当前阶段拆分独立仓库。只有在移动端明确改用 Flutter、Swift 或 Kotlin 等无法复用 React 的技术栈，或团队/权限/发布节奏必须隔离时，才重新评估。

### 2.2 技术选型

| 平台 | 方案 | 用途 |
| --- | --- | --- |
| Web | 现有 React + Vite + PWA | 浏览器访问、可安装 Web 应用 |
| Windows/macOS | Tauri 2 | 将现有 React 应用包装为桌面安装包，并提供文件、菜单、自动更新等系统能力 |
| iPhone/iPad/Android | Capacitor | 将现有 React 应用包装为移动 App，并接入移动系统的文件选择、分享和安全区域能力 |

选择 Tauri 而非另写 Electron 客户端，是为了在保留 Web 技术栈的同时减小桌面安装包和运行开销。移动端先使用 Capacitor；若未来阅读渲染性能或平台特性无法满足，再评估局部原生模块，而不是立刻重写整个应用。

### 2.3 不变的服务端边界

认证、同步、翻译、解释、OCR 和额度控制继续使用现有服务端边界。所有端都必须遵守：

- AI/OCR 供应商密钥只能保存在服务端，不能写入安装包或客户端代码；
- 仅在用户主动操作时发送选区或当前页，不能上传整本书；
- 默认同步元数据、进度、摘录和设置；原始 EPUB/PDF 仅在用户明确开启端到端加密云备份后上传，完整规则见 `docs/user-data-sync-architecture.md`；
- 同步表、RLS 与远端白名单以 `src/lib/remote.ts` 和现有 migration 为准。

## 3. 哪些代码复用，哪些代码分别实现

### 3.1 共享代码

以下能力应尽可能维持一份实现：

- React 页面、组件、样式和 i18n；
- EPUB.js / PDF.js 阅读与选区逻辑；
- Work、Edition、阅读位置、摘录、笔记等领域模型；
- 翻译、解释、OCR、认证和同步的请求协议；
- 冲突处理和本地导入/导出数据格式。

### 3.2 平台适配代码

下列功能不能只靠前端页面完成，必须按平台单独实现：

| 能力 | Web/PWA | 桌面端 | 手机/iPad |
| --- | --- | --- | --- |
| 导入书籍 | 浏览器文件选择器 | 文件选择器、拖拽、文件关联 | 系统“文件”选择、分享菜单、AirDrop 导入 |
| 原书保存 | OPFS / IndexedDB | 应用数据目录中的受控文件 | App 沙盒文件目录 |
| 元数据与缓存 | IndexedDB | 本地数据库（建议 SQLite） | 本地数据库或受控移动端存储 |
| 更新 | Service Worker 更新应用壳 | 原生自动更新 | App Store / Google Play 发布更新 |
| 系统交互 | Web Share 等浏览器能力 | 原生菜单、快捷键、拖拽 | 触摸、横竖屏、安全区域、后台恢复 |

平台差异必须收敛在统一的“平台能力层”中，业务页面不能直接调用 Tauri、Capacitor 或浏览器专属 API。

## 4. 推荐目录演进

当前仓库不需要立刻大规模移动代码。按以下渐进方式演进：

```text
WorLibrary/
  src/                         # 现有 Web 阅读器；逐步提取可共享模块
  apps/
    desktop/                   # Tauri 配置和桌面专属适配
    mobile/                    # Capacitor 配置和移动端专属适配（开始移动端时创建）
  packages/                    # 仅当跨端代码稳定且规模足够后再创建
    reader/                    # 可复用的阅读领域逻辑
    storage/                   # 跨端存储接口、数据模型与迁移
    platform/                  # 平台能力接口和各端适配器
```

初期允许 `src/` 继续作为共享前端来源。只有实际出现多个端都要使用的稳定代码时，才抽到 `packages/`，避免为“未来可能需要”而过早重构。

## 5. 平台能力层约定

需要创建统一接口，例如：

```ts
interface PlatformServices {
  pickBookFiles(): Promise<File[]>;
  saveBook(file: File): Promise<BookFileReference>;
  readBook(ref: BookFileReference): Promise<Blob>;
  deleteBook(ref: BookFileReference): Promise<void>;
  exportReadingData(): Promise<void>;
}
```

- Web 实现继续使用当前 OPFS / IndexedDB 和浏览器文件 API；
- Desktop 实现通过 Tauri 的最小权限命令访问应用数据目录；
- Mobile 实现通过 Capacitor 的文件系统和文件选择插件访问 App 沙盒；
- 组件与 `App.tsx` 只依赖接口，不导入平台 SDK；
- 原生侧暴露的文件路径、命令和权限必须最小化，禁止任意路径读写。

接口名称可随实现调整，但“领域/UI 与平台 SDK 隔离”的原则不可改变。

## 6. 数据与跨设备体验

### 6.1 默认同步内容

登录并开启同步后，跨设备同步：

- 作品与版本元数据；
- 阅读进度；
- 摘录、笔记和颜色；
- 设置与必要的 AI 结果缓存元数据。

### 6.2 原书文件策略

原始 EPUB/PDF 默认只保存在导入它的设备。用户明确开启“加密云备份”后，客户端才会分块加密并上传至用户私有备份桶；新设备登录、使用恢复码解锁后可按需恢复原书。具体数据模型、密钥、冲突、配额、删除与接口约定以 `docs/user-data-sync-architecture.md` 为准。

浏览器本地数据不能自动进入桌面或移动 App。因此桌面端和移动端仍必须提供“导出阅读数据 / 导入阅读数据”迁移路径；该迁移不等同于同步。未完成云备份实现前，不得悄悄复制原书或宣称自动恢复。

## 7. 实施顺序

### 阶段 A：稳固 Web/PWA 基线

- 保持 EPUB/PDF 导入、离线阅读、进度和摘录可靠；
- 维护 PWA 的安装、离线和更新体验；
- 识别并抽象浏览器专属的文件/存储调用。

### 阶段 B：桌面 MVP（优先）

- 在 `apps/desktop` 初始化 Tauri 2；
- 让现有阅读器在桌面窗口中启动；
- 支持导入、拖拽导入和应用私有目录保存 EPUB/PDF；
- 完成桌面端进度、摘录、删除和备份恢复；
- 再接入认证、同步、翻译和 OCR；
- 最后加入菜单、快捷键、文件关联、签名与自动更新。

### 阶段 C：移动端 MVP

- 在 `apps/mobile` 初始化 Capacitor；
- 先保证书架、阅读、进度、摘录和同步可用；
- 接入 iOS/iPadOS/Android 文件导入和系统分享；
- 适配触摸选区、横竖屏、安全区域和后台返回恢复；
- 分别在真机 iPhone、iPad 和 Android 上验证大文件导入和长时间阅读。

### 阶段 D：跨端体验完善

- 完善冲突提示与“继续阅读”行为；
- 评估用户明确开启的加密书籍备份；
- 建立各平台的发布、签名、更新和崩溃监控流程。

## 8. 每次实现时的验收清单

涉及任一客户端时，至少验证：

- 导入 EPUB、文本型 PDF，重启后仍可打开；
- 阅读位置、摘录、笔记能正确恢复；
- 删除一本书不会删除其他本地数据；
- 离线时已导入书籍可读，联网能力有清楚的降级提示；
- 登录同步不会上传原始书籍；
- AI/OCR 请求不携带供应商密钥，不发送整本书；
- Web、桌面和移动端的 UI 改动分别检查适合其屏幕与输入方式；
- 运行对应的类型检查、构建及自动化测试，并补充风险相称的测试用例。

## 9. 首个可执行任务

首个跨端开发任务应是“桌面端技术验证”，而不是一次性完成完整客户端：

1. 新增 `apps/desktop` 的 Tauri 工程；
2. 使用开发模式加载现有 React 应用；
3. 只实现一个受控的 EPUB/PDF 文件选择与读取通路；
4. 验证导入、重启、重开同一本书和删除；
5. 确认该通路不会破坏现有 Web 的 OPFS / IndexedDB 行为；
6. 记录 Tauri 权限、开发命令、打包命令和测试结果到相关运行文档。

通过技术验证后，再将平台能力层推广到现有存储、同步和 UI 流程。
