# WorLibrary 技术架构方案

> 版本：MVP 草案 · 目标读者：产品创始人、前端开发者与没有后端经验的协作者

## 1. 这份文档解决什么问题

WorLibrary 是一个面向多语言深度阅读者的 Web 阅读器。用户导入自己拥有或有权使用的 EPUB、PDF、MOBI、CBZ 文件；在阅读时划线，即可按自己设定的“理解语言”获得翻译和通俗解释。用户还可将同一作品的原文和多个译本关联，并在单栏或双栏中阅读。

第一阶段的目标是可公开试用的 MVP，而不是完整的云图书馆。因此本方案采用 **本地优先、轻后端**：书籍和大多数阅读数据默认保留在用户自己的浏览器；后端不是替用户保存图书馆，而是代管平台 AI 密钥、控制付费能力、调用外部 AI/OCR 服务。

## 2. 产品边界

### MVP 要做

- 本地导入 EPUB、PDF、MOBI、CBZ；首发承诺稳定支持 EPUB 与文本型 PDF，MOBI/CBZ 作为实验性兼容目标逐步验证。
- 保存书架、独立阅读进度、划线、笔记和已经生成的 AI 解释。
- 设置理解语言；划线文本返回“翻译 + 通俗解释”。
- 对有可选择文字的 EPUB、MOBI 和文本型 PDF 直接使用 AI。
- 对扫描 PDF 与 CBZ 提供用户主动触发的“识别文字”入口（OCR）。
- 将不同语言版本关联为同一作品；支持版本切换和双栏对照。
- AI 段落对齐失败时，回退为同章节的双栏独立滚动。
- 中英文界面、匿名每日试用额度、基本错误监控。

### MVP 暂不做

- 不提供、抓取或分发未经明确授权的书籍来源；首发仅使用本地导入文件。
- 不要求登录，不做跨设备同步，不做支付或订阅。
- 不默认上传整本书、整份 PDF 或用户的完整书架。
- 不承诺扫描图片/漫画的全自动段落对齐。

## 3. 一张图理解系统

```text
用户浏览器（阅读器 PWA）
  ├─ 本地书籍、进度、划线、AI 结果、译本关系
  ├─ EPUB/PDF/MOBI/CBZ 阅读与双栏显示
  └─ 仅在用户主动请求时发送少量文字或当前页图片
                         │
                         ▼
API 网关（MVP 推荐 Cloudflare Worker）
  ├─ 检查免费次数、请求长度与异常流量
  ├─ 保存平台的 AI 密钥，安全调用模型
  ├─ 调用 OCR 服务
  └─ 返回翻译、解释或识别文字
                         │
          ┌──────────────┴──────────────┐
          ▼                             ▼
数据库（Supabase）                 AI / OCR 服务
用户、额度、未来同步元数据         翻译、解释、图片文字识别
```

## 4. 推荐选型：它们分别有什么作用

| 服务 | 用通俗的话说 | 负责什么 | 为什么选择它 |
| --- | --- | --- | --- |
| Next.js + PWA | 阅读器的大厅 | 用户看到的网页、导入、阅读、划线和设置 | 当前 Demo 可逐步升级；PWA 可安装到手机桌面，也能提供离线体验。 |
| 浏览器本地存储（IndexedDB / OPFS） | 用户自己的书包 | 保存书籍、阅读进度、划线和缓存结果 | 不必先建立云书库；减少存储费用、版权风险和用户隐私顾虑。 |
| Cloudflare Worker | 接待员 | 接收请求、检查额度、转交 AI/OCR、隐藏密钥 | 不需要维护传统服务器；适合请求量不稳定的公开 MVP。它是本方案首发的网关选择，而不是与 Next.js Server 同时建设。 |
| Supabase | 现成的会员系统和登记簿 | 后续登录、数据库、额度记录、同步元数据 | 对新手友好，避免自己搭建数据库和账号系统。MVP 可只使用数据库部分。 |
| AI API | 语言老师 | 翻译、解释、总结、将来用于段落对齐 | 无需训练和部署自己的大模型；可按用量付费。 |
| OCR 服务 | 识字员 | 从扫描 PDF 或漫画页面图片中找出文字 | 让不能直接划线的页面也能在用户需要时进入 AI 流程。 |
| R2 / S3 对象存储 | 未来的大型仓库 | 未来用户主动开启云同步时存书籍文件 | 大文件不适合塞进数据库；先不接入，等同步需求明确再启用。 |
| Sentry 或同类工具 | 报修系统 | 收集浏览器与 API 的报错 | 用户遇到问题时可定位问题，而不是只收到“打不开”的反馈。 |

## 5. 为什么需要 API 网关

API 网关不是另一个“复杂系统”，它就是一小层后端接待员。它必须存在的主要原因是：**平台购买的 AI 密钥不能放进网页代码。** 若直接放进网页，任何访客都能在浏览器中取走密钥，再用你的账户无限调用 AI，产生费用。

这里的“环境变量”指只保存在 Cloudflare 后台配置中的秘密值，例如 AI 密钥；网页用户看不到它。网关可以检查请求是否像来自 WorLibrary，但不能因此证明对方一定是真人或无法被模仿，所以还需要额度、频率限制和必要时的人机验证共同提高滥用成本。

一次划线解释只应传递当前需要处理的少量内容：

```json
{
  "action": "explain",
  "selectedText": "Freedom is a word with a thousand meanings.",
  "contextBefore": "前面一两句话（可选）",
  "contextAfter": "后面一两句话（可选）",
  "sourceLanguage": "en",
  "targetLanguage": "zh-CN"
}
```

网关按顺序执行：

1. 确认请求来自 WorLibrary 网页，并检查是否超过每日免费次数。
2. 检查文字长度、请求频率和异常重复调用。
3. 加上固定指令，例如“翻译为简体中文，并使用通俗语言解释”。
4. 使用保存在服务器环境变量中的密钥调用 AI。
5. 返回翻译与解释；浏览器将结果保存到用户本地。

默认不发送整本书、全部笔记、完整书架或设备上的其他文件。用户点击“识别文字”时，才上传当前页图片给 OCR；应限制图片尺寸，并在处理后尽快删除临时文件。

## 6. 关键数据如何保存

### 浏览器本地保存（MVP 的主要数据）

| 数据 | 说明 |
| --- | --- |
| `Work` | 一个抽象作品，例如《局外人》；可拥有多个语言版本。 |
| `Edition` | 某一个具体文件与版本，例如法文原版或中文译本；各自有独立阅读进度。 |
| `Highlight` | 用户划线的位置、文本、颜色与备注。 |
| `AIExplanation` | 某段划线对应的翻译、解释、目标语言和生成时间。 |
| `Alignment` | 两个版本之间的章节或段落匹配；带置信度，低置信度不可强制同步。 |

### 服务端保存（MVP 的最小数据）

| 数据 | 用途 |
| --- | --- |
| 匿名设备标识的散列值 | 计算试用额度；它是不可直接还原的标记，不是用户账号。清除浏览器数据、换设备或使用隐私模式，可能被视为新的试用者。 |
| 每日 AI/OCR 用量 | 限制成本与滥用。 |
| 请求时间、状态和错误类型 | 排查故障和异常流量。 |

不要在服务端日志中记录完整书籍内容、用户划线原文或 AI 密钥。运行日志只保留脱敏后的状态和错误类型，并设定短保留期（例如 30 天）；具体期限和访问权限需在上线前确定。

## 7. 两种重要流程

### 7.1 划线翻译与解释

```text
用户选中一句话
  → 浏览器读取选区、来源语言、理解语言与少量上下文
  → API 网关检查额度和安全规则
  → AI 返回翻译 + 通俗解释
  → 浏览器展示结果并存到本地
```

如果用户设定的理解语言是中文，那么无论划线的是英语、日语、法语还是其他可处理语言，结果都默认输出中文。对于 PDF/CBZ 图片，用户需先点击识别文字；OCR 产出可选中文本后，流程与普通文字相同。

### 7.2 多译本对照

```text
用户导入原文与译本
  → 系统按书名、作者、ISBN、语言生成关联建议
  → 用户确认它们是同一作品
  → 分别保存版本与独立进度
  → 用户打开双栏模式
  → 后台尝试匹配章节/段落
  → 置信度足够：精确对齐；否则：同章节独立滚动
```

书名只能用于“建议关联”，不能直接自动绑定，因为不同书可能同名、不同版可能副标题不同，且很多本地电子书没有可靠 ISBN 或元数据。用户确认始终是必要步骤。

## 8. 分阶段实施

### 阶段 A：可真实使用的本地阅读器

- 将静态 Demo 迁移至 Next.js/PWA。
- 接入阅读/解析引擎，先优先保证 EPUB 与文本型 PDF；MOBI、CBZ 作为实验性兼容目标逐步验证。
- 用浏览器本地存储持久化书籍与进度。
- 完成书架、导入、划线、译本手动关联和单栏阅读。

### 阶段 B：AI 公开试用

- 创建 API 网关与 `POST /api/ai/explain`。
- 接入一个 AI 服务，完成翻译 + 通俗解释。
- 设置每日额度、请求长度限制、基础频率限制与错误监控。
- 加入明确的隐私提示：仅发送用户选择的文字和必要上下文。

### 阶段 C：OCR 与双栏对照

- 创建 `POST /api/ocr/page`，用户主动上传当前页图片。
- 将 OCR 识别结果显示为可选文本。
- 增加版本切换、双栏显示、章节匹配和对齐失败回退。
- 将高耗时的 OCR 与段落匹配改为异步任务，避免阅读页面长时间等待。最初任务状态可保存在浏览器本地：用户离开页面后任务停止，重新打开可重试；只有未来需要“关闭页面后仍继续处理”时，才引入服务端队列与任务表。

### 阶段 D：账号与同步（确认需求后才做）

- 用 Supabase Auth 加入登录。
- 同步用户偏好、进度、划线和 AI 结果。
- 只有用户主动启用时，才用 R2/S3 保存加密的书籍副本。
- 增加设备冲突处理、删除数据和导出数据功能。

## 9. 成本、安全与隐私底线

- 为 AI 和 OCR 设置月度预算提醒与单用户每日上限；免费额度先保守，再根据真实成本调整。
- 前端永远不存平台 AI 密钥；密钥只存在 API 网关的环境变量中。
- 对匿名请求使用设备标识、IP 频率限制和人机验证的组合；不要将单一 cookie 当作完整安全方案。这只能提高批量滥用成本，不能彻底阻止用户清理数据或轮换网络后重新获得额度。
- 提供明确告知：请求 AI 时会发送被选中的文字；请求 OCR 时会发送当前页图片。本服务不应持久化这些图片；第三方 OCR 供应商可能有自己的数据保留政策，选型时必须确认其条款。
- 为用户提供删除本地书籍、划线和缓存结果的入口；账号同步上线后还要提供云端删除与导出。
- 日志只记录必要的运行信息，避免存完整书籍内容、完整选区文本和敏感凭据。

## 10. 当前决策与待决策项

### 已决定

- Web 优先、个人深度阅读者优先。
- 支持多语言内容；界面首发支持中文和英文。
- 首发稳定支持 EPUB 与文本型 PDF；MOBI、CBZ 是后续逐步验证的兼容目标。AI 的核心交互是划线后的翻译与通俗解释。
- 用户可设置理解语言。
- 书籍本地优先并支持离线阅读。
- 不接入外部书源；不实现 Z-Library 的连接、抓取或下载。
- 公开 MVP 使用匿名每日免费额度。

### 在开始真实后端前需确认

1. 首发的 AI 供应商与可接受的月度预算。
2. OCR 供应商、支持的语言和每页可接受的等待时间。
3. 免费额度：每天可解释多少次、可 OCR 多少页。
4. 首批支持的浏览器范围，以及是否同时优先支持移动端。
5. 何时需要用户登录与跨设备同步。

## 11. 成功标准

MVP 可以称为“可公开试用”，至少要满足：

- 用户在桌面和移动浏览器中能导入一本合法拥有的 EPUB 或文本 PDF，刷新或断网后仍能继续阅读。本地数据依赖浏览器可用空间，用户清理站点数据后会丢失，因此需要显示存储状态并在后续提供导出/备份。
- 用户划线一段可选文本后，能稳定获得其理解语言的翻译和通俗解释。
- 用户无法从网页代码中取得平台 AI 密钥；每日额度、频率限制和人机验证能提高滥用成本，但不承诺完全杜绝绕过。
- 用户能手动关联同一作品的两个版本、分别保存进度，并在双栏中阅读。
- AI/OCR 失败、网络中断或低置信度对齐不会造成阅读器崩溃，并会给出清晰提示。
